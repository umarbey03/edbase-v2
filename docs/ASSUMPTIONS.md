# Assumptions log

One line per decision that was made without asking the project owner:
`- [date] <question> -> <decision> -> <reason>`

- [2026-09-03] Mobile browsers have no `getDisplayMedia` — hide the screen-share button or keep it? -> Keep it visible and explain on tap -> A missing button makes the teacher hunt for it and conclude the app is broken; screen share is the core teaching tool, unlike the fullscreen button which may be hidden silently.
- [2026-09-03] Fullscreen scope: `<main>` (video only) or the whole page? -> The whole page root -> Outside the fullscreen element nothing is painted, so the participants/chat panel was unreachable while presenting. In fullscreen the panel becomes a floating drawer, so the video still gets the full width.
- [2026-09-05] Recording pipeline v2, code comment language: SPEC Open Question 7 recommends English for new files, but every neighbouring file in `Recordings/` carries Uzbek doc-comments -> Uzbek doc-comments in the new recording files (identifiers and user-facing strings unchanged) -> Owner ruled the module must be internally consistent; a mixed-language module is worse than either choice applied consistently.
- [2026-09-05] `RecordingTrack.MarkCompleted` — reuse `SessionRecording`'s "only `Completed` is final" guard, or block every terminal state? -> Block every terminal state (a `Failed` track is never resurrected) -> A track is `Failed` because storage did not have the object; a late `egress_ended` would point the night job at a file that does not exist and fail the whole recording instead of losing one segment. SPEC §8 names this behaviour explicitly.
- [2026-09-05] Where the composition give-up limits live — in the M6 job or in the entity? -> `SessionRecording.MaxCompositionAttempts` / `MaxCompositionInterruptions` constants plus `CanRetryComposition` / `CanResumeComposition` predicates, with the counters still incremented by the methods SPEC §5.1 names -> The signatures stay exactly as specified, but the two thresholds and the comparison direction cannot be got wrong in the job; the "interruption is not a failure" rule is the whole point of having two counters.
- [2026-09-05] `RecordingTrack` needs a way to record a non-terminal start failure, which SPEC §5.1's method list omits -> Added `RecordAttemptError`, copied verbatim from `SessionRecording` -> Without it the reconcile job would either assign `Error` directly (bypassing the 500-char trim and overflowing the column) or misuse `MarkFailed` and kill a retryable row.
- [2026-09-05] `IRecordingStorage.OpenReadAsync` — reuse `IMediaStorage`'s `StoredMedia`, or define a return type of its own? -> New `StoredRecordingObject` (stream + size + ownership) -> `StoredMedia` carries `IsPartial`/`TotalLength`, which only mean anything for `Range` requests; this path deliberately has no `Range` (ffmpeg must not go back to the network), so those two fields would sit at a constant value and invite the reader to conclude partial reads exist here. The signing and URL logic still lives in `S3SigV4`, in one place.
- [2026-09-05] SPEC-RECORDING-V2 §5.9-3 claims `Compose` dropping `LargeUploadTimeoutSeconds` makes it "fall back to the 60 s default" — in the code that property's own default is 1800 s -> Added the missing line anyway and recorded the SPEC inaccuracy in the comment beside it -> The real defect is narrower: an environment-supplied value (`Storage__LargeUploadTimeoutSeconds`) was silently discarded once the database snapshot loaded, so an operator could not raise the limit at all. The fix stays inside what §5.9 permits and changes no behaviour otherwise.
- [2026-09-05] SPEC §5.3 gives `ILiveKitEgress` exactly two new methods, but §4.1 needs `ListParticipants`/`ListEgress` from a job in the Application layer, which cannot see `LiveKitEgressClient` -> Added a second, read-only port `ILiveKitRoomQuery` (both methods), implemented by the same `LiveKitEgressClient` -> Keeps §5.3's method list literally intact, keeps the "controls recording" port from being handed to callers that only read state, and avoids duplicating the Twirp/token/error plumbing in a second class.
- [2026-09-05] How `ListParticipantsAsync`/`ListEgressAsync` report a LiveKit failure -> Explicit result records (`LiveKitTrackListResult`, `LiveKitEgressListResult`) with a `Succeeded` flag, mirroring `EgressStartResult`; an empty list means "nothing running", never "the call failed" -> An empty list on failure would make the reconcile job conclude the audio mixer had died and start a replacement over a still-running one, i.e. two audio files and doubled voices in the night composition.
