- [2026-09-10] SPEC-RECORDING-V2 §9.1 layer 1 asked for the empirical `RoomAudio` drift rate after ~10 lessons; 12 composed lessons (recordings 147-161) were read out of the compositor log -> every one of them exceeds the SPEC's 0.1% "revise the design" line: 0.14, 0.37, 16.68, 1.65, 0.90, 0.14, 0.49, 0.56, 0.53, 2.48, 0.82, 1.54 % (media duration short of the wall-clock span by 5.5 s to 123 s). Cause is upstream, not in the planner: the egress room mixer logs `sdk/appwriter.go:483 buffer full, dropping sample` in bursts (e.g. `EG_y2Znw3vaiZeD`: 136 of its 176 drops inside one minute) plus `synchronizer/track.go:548 ignoring sender report with unacceptable drift`, so the .ogg loses timeline without leaving a PTS gap -> `recordings.compose_audio_offset_ms` cannot fix this and must not be used to try: the offset is neither constant nor a clean slope but a staircase, so audio runs ahead of video by whatever has been lost so far (recording 157 = ATF 184 dars 12: -30.7 s over 91.5 min, ~4.7 s by minute 14, which is the complaint that surfaced it). `aresample=async=1` in `AudioTail` fills PTS gaps only and there are none to fill; the §9.1 layer 2 output check compares total duration against the timeline, which the video stream satisfies on its own, so a 30 s short audio stream passes it.
- [2026-09-10] A LiveKit egress that is killed mid-lesson reports `EGRESS_COMPLETE` with `error: ""` and a real file key, so `MarkCompleted` made an 8-minute recording of a 60-minute lesson indistinguishable from a healthy one (2026-09-09, ATF 195 — 2-dars; `endReason: "CPU exhausted"`, cpu 1.604 vs the `room_composite_cpu_cost: 1.30` that LiveKit also uses as its kill threshold) -> added `SessionRecording.MarkTruncated`, called from `RecordingWebhookHandler.Complete` when `StopRequestedAt is null` and the session is still `Live`; the file stays `Completed` and the reason (with LiveKit's `details`) goes into `Error`, which the card already renders -> the discriminator is "did WE ask it to stop", not a duration threshold: a lesson legitimately runs shorter or longer than scheduled, so any percentage-of-scheduled rule would either cry wolf or miss the real case. `MarkFailed` was deliberately not reused — hiding the 8 minutes that *were* recorded is a second loss on top of the first.
- [2026-09-10] The §9.1 layer-1 drift check only wrote a log line, so a recording whose audio spine is 30 s short shipped with no mark on it at all and the defect was found by a student, not by us -> `RecordingCompositionRunner.ApplyProbes` now returns a staff-visible warning for the `RoomAudio` row only, merged into `CompositionError` beside the existing "Dars ovozi yozib olinmadi." -> `RoomAudio` only because §9.1's own reasoning says the audio is the timeline and lip-sync is judged against it; promoting video-segment drift too would put a red block on nearly every card (almost every measured lesson has a video segment a few seconds off) and staff would stop reading the block entirely. - [2026-09-10] The room-audio file is shorter than its wall-clock window on every measured lesson, and §9.1's premise ("one continuous audio file spans the whole lesson") is therefore wrong -> the planner stretches the audio onto its own window with `atempo` (pitch-preserving), gated by a 0.05% dead band and a 5% ceiling; the ratio comes from `RecordingTrack.ProbedDurationMs`, and because that is only knowable once the file is on disk, the composer returns `CompositionResult.NeedsRePlan` **before encoding** and the runner re-plans in the same cycle -> three alternatives were rejected: `compose_audio_offset_ms` (corrects a constant, this is a slope), `aresample=async=1` (fills PTS gaps, and a short file proves there are none — a gap-preserving file would still report the full duration), and a second full encode (the night window is already the binding constraint; re-planning before the encode costs one extra download instead). Flat stretching cannot restore *where* the time was lost, which the file does not record, but it is bounded: the offset is zero at both ends and the worst case (all loss in one instant) is no worse than today, while the measured loss is spread across dozens of small clusters, so in practice it lands near optimal. Above 5% the file is broken rather than skewed (worst measured: 16.7%, 90 s missing from a 542 s lesson) and stretching it would disguise "the audio was not recorded" as "the teacher sounds strange", so those pass through uncorrected and carry the `CompositionError` warning instead.
